01

Baseline — confirm the limit is enforced

LOGIC

Establish ground truth before trying to break it.

Expected: 4th admin request rejected with an error/limit message; admin count stays at 3.
02

Basic race condition — parallel curl

RACE

Fire several enable requests near-simultaneously to see if the count check has a TOCTOU gap.

Expected (if vulnerable): more than 3 admins end up active because each request read the same pre-update count.

04

Race condition — hey / load tool

RACE

Quick concurrency hammer without Burp.

Expected: check final admin count after burst; inconsistent per-run results is a strong race-condition signal.
05

Duplicate query parameter

PARAM POLLUTION

Some frameworks validate the first occurrence but process the last (or vice versa).

Expected: server enables id={ID} despite validating against the already-legitimate id=3.
06

Array-style parameter

PARAM POLLUTION

Test if the endpoint (or an underlying framework default) accepts array syntax and bulk-processes it.

Expected: both IDs get enabled in one request, only counted once by the limit check.
07

Comma-separated IDs

PARAM POLLUTION
Expected: backend splits on comma and loops without re-checking count per item.
08

URL-encoded ID value

PARAM POLLUTION

Check if WAF/validation regex is bypassed by encoding while the app-layer parser still decodes correctly.

Expected: identical behavior to plain "4" — flags any front-end filter that doesn't decode before checking.
09

Parameter name case variation

PARAM POLLUTION
Expected: case-insensitive frameworks still process it while a case-sensitive validation layer misses it.
10

Path case variation

LOGIC
Expected: routing layer normalizes case but a separate access-control middleware doesn't match the route, skipping the check.
11

HTTP verb confusion

LOGIC

The limit check might be bound to GET specifically.

Expected: one of the alternate verbs succeeds where GET is blocked (or reveals an entirely separate code path).
12

Direct IDOR — edit user object instead of using the enable endpoint

IDOR
Expected: the count/limit logic lives only in the dedicated "/enable" endpoint and is absent from the generic user-update endpoint.
13

Toggle abuse — disable one, enable two in close sequence

RACE
Expected: count check reads stale state mid-transition, letting both new admins through before the disable commits.
14

Client-side-only validation check

LOGIC
Expected: if the "max 3" logic is only referenced in JS (e.g. disabling a button), replaying the raw request bypasses it entirely.
15

CSRF exploitability — GET request with a side effect

CSRF

Since state changes via GET with no visible token, test if a third-party page can trigger it silently.

Expected: loading this from an attacker-controlled page while an admin session is active silently promotes user {ID} — flag regardless of the limit-bypass outcome.
16

Response caching / link-prefetch replay

LOGIC
Expected: absence of no-store/no-cache headers means a browser prefetch, proxy cache, or shared link could unintentionally replay the state-changing GET.
17

Cross-session simultaneous promotion

RACE

Two different authenticated admin sessions each try to promote a different 4th admin at the same instant — tests whether the count check is enforced at the DB layer (locked) or app layer (racy).

Expected: both succeed, resulting in 5 active admins — indicates missing DB-level unique constraint/lock, not just app-layer race.
18

Negative / non-numeric / boundary ID values

LOGIC
Expected: unexpected input types cause the count-check logic to throw/skip while the enable logic downstream still executes (fail-open behavior).
19

Trailing slash / fake extension trick

LOGIC
Expected: reverse proxy / route-matching rule for the "protected" path doesn't match the modified path, so it falls through to the handler without middleware checks.
20

Burp Repeater — grouped "Send group in parallel"

RACE

Manual UI-based alternative to Turbo Intruder for the same race window test.

1. Capture the GET enable request in Burp Proxy.
2. Send to Repeater, duplicate the tab 3-4 times, edit each user_id.
3. Select all tabs → right-click → "Send group in parallel" (single-packet mode if available).
4. Compare response codes/bodies and check final admin count.
